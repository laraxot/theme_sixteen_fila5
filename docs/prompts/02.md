# Workflow BMAD Design Comuni Sixteen

## 1. Vincoli non negoziabili

- Sixteen è già il tema Design Comuni: non creare un secondo tema, un layout `design-comuni` o wrapper duplicati `pub_theme::components.blocks.*.design-comuni`.
- Usare esclusivamente TailwindCSS, Alpine.js, Lit, DaisyUI e Flowbite. Non importare Bootstrap Italia, CSS Bootstrap, sprite Bootstrap o CDN Bootstrap.
- I contenuti devono arrivare dai JSON tenant. La Blade contiene rendering e accessibilità, non testi, URL, immagini o fixture hardcoded non dichiarate dal contratto dati. I testi statici di riferimento (label, placeholder, step) vanno esposti come chiavi JSON con default in Blade, mai come chiavi di traduzione inesistenti (`__('fixcity::...')` mostra la chiave se il file lang manca).
- Header e footer restano sezioni CMS: `<x-section slug="header" />` e `<x-section slug="footer" tpl="full" />`. I dati sono in `laravel/config/local/fixcity/database/content/sections/`.
- Gli script nuovi vivono sotto `bashscripts/`; la documentazione degli script vive sotto `bashscripts/docs/`. La documentazione specifica del tema vive sotto `laravel/Themes/Sixteen/docs/`.
- Le route e gli URL nei JSON usano route Laravel/Folio (`route(...)` o il contratto CMS), mai path statici quando esiste una route applicativa.

## 2. Pre-flight obbligatorio

Prima di modificare codice:

1. Identifica repository e working directory: `/mnt/nas07/var/www/_bases/base_fixcity_fila5`.
2. Leggi `bmad-output/project-context.md`, `bmad-output/decision-log.md`, l'architettura disponibile, la story interessata e la documentazione Sixteen correlata.
3. Cerca con `rg` e, se disponibile, QMD/Graphify: slug, JSON, blocchi, layout, sezioni, chiamanti, test, report e decisioni già esistenti.
4. Cerca nella memoria Hindsight le convenzioni e le decisioni pertinenti; leggi le pagine rilevanti prima di re-derivare una regola.
5. Scarica la reference e la pagina locale in `/tmp/parity/ref` e `/tmp/parity/local`, confronta DOM e computed styles. Non basarti sulla sola ispezione visiva.
6. Elenca file posseduti dalla modifica e possibili impatti su callers, fixture, cache Blade, build e route.

Se lo scope è una nuova capability o cambia materialmente, registra/aggiorna l'iniziativa Hindsight prima di scrivere codice. Per bug, piccole correzioni e refactor locali non creare iniziative artificiali.

## 3. Ciclo BMAD corretto

### Analysis e planning

Usa brainstorming o ricerca solo quando manca una decisione. Produci o aggiorna `SPEC.md`, PRD/tech-spec e decision log con problema, capability, vincoli, non-goal e metriche.

### Solutioning

Usa l'architettura BMAD per documentare confini, flusso dati, blocchi riusabili, layout, sicurezza, responsive e WCAG. Non usare il documento di planning come scusa per introdurre codice duplicato.

### Stories

Ogni story deve essere piccola e autonoma e contenere:

- URL reference e URL locale;
- screenshot/DOM di riferimento;
- blocchi DOM e gerarchia heading;
- schema JSON e mappa JSON → Blade → HTML;
- file/module scope esplicito;
- acceptance criteria HTML, visual, responsive e WCAG;
- comandi di verifica e risultato atteso;
- dipendenze e blocker verificabili.

La story è `ready-for-dev` solo quando ha acceptance criteria testabili, testing strategy e owned scope. La skill di epics/stories pianifica; l'agente di implementazione modifica il codice; la review verifica l'insieme.

## 4. Contratto JSON, layout e blocchi

Ogni pagina dinamica deve avere almeno:

```json
{
  "id": "tests.<slug>",
  "slug": "tests.<slug>",
  "layout": "test",
  "content_blocks": {"it": []}
}
```

`layout` assente significa layout applicativo di default; `layout: "test"` significa `<x-layouts.test>`. La scelta del layout va fatta a monte dalla pagina/composizione prevista dal progetto: nelle Blade di pagina usare direttamente il layout corretto, non aggiungere `Page::findUniqueBySlug`, `match` o un dynamic component per replicare una decisione già nota.

`pub_theme` è il namespace Sixteen. Un blocco deve avere un nome semantico e possedere una sola responsabilità, ad esempio `components.blocks.form-wizard`, `components.blocks.segnalazioni-elenco` o `components.blocks.template-index`. Prima di creare un blocco, cercare e riusare quello esistente.

### Risoluzione slug (critica)

La route `tests.view` mappa l'URL `/it/tests/<slug>` al pageSlug `tests.<slug>`. Il file JSON in `database/content/pages/` deve avere `id` e `slug` uguali a `tests.<slug>`. `[slug].blade.php` non contiene fallback, cataloghi o include per slug speciali: passa sempre il contratto a `<x-page>`. Per aggiungere una pagina: crea `tests.<slug>.json` con lo slug corretto e i blocchi necessari; verifica che il markup provenga dal componente CMS e non da una Blade per-pagina.

## 6. Struttura blocchi per tipo di pagina

Ogni pagina di servizio (segnalazione) ha questa gerarchia:

1. `cmp-breadcrumbs` — `Home / Servizi / <pagina>` (col-12 col-lg-10)
2. `cmp-heading` — h1 `title-xxxlarge` + stepper (col-12 col-lg-10 / col-12)
3. `steppers` — `steppers-header` con `ul` di step (confirmed/active/pending) + `steppers-index` `N/3`
4. Contenuto step — card `has-bkg-grey` con `card-header` (h2/h3) e `card-body`
5. `cmp-nav-steps` — nav `steppers-nav` con Indietro / Salva / Invia
6. `bg-grey-card shadow-contacts` — card `cmp-contacts` con `contact-list` (FAQ, assistenza, numero verde, appuntamento)

La sidebar `cmp-navscroll` (col-lg-3, `hidden lg:block`) contiene l'accordion `INFORMAZIONI RICHIESTE` con link agli anchor `#report-place`, `#report-info`, `#report-author`.

## 7. Header, footer e accessibilità

Per ogni campo in `header.json` e `footer.json` documentare l'elemento HTML risultante: logo, nome, slogan, regione, lingua, accesso, navigazione primaria/secondaria, social, ricerca, colonne, contatti, legali e copyright.

Ogni controllo deve avere nome accessibile, focus visibile, target almeno 44×44px, stato attivo esplicito, tastiera completa e contrasto almeno 4.5:1 per testo normale e 3:1 per componenti/UI. Verificare anche il footer scuro, il cambio lingua, le icone e i link senza sottolineature involontarie.

## 8. Verifica visiva e WCAG

Per ogni pagina eseguire reference e locale almeno a 375, 768 e 1440 CSS px:

```bash
# Download reference e locale per il diff
mkdir -p /tmp/parity/ref /tmp/parity/local
curl -s "https://italia.github.io/design-comuni-pagine-statiche/sito/<slug>.html" -o /tmp/parity/ref/<slug>.html
curl -s "http://192.168.1.40:8000/it/tests/<slug>" -o /tmp/parity/local/<slug>.html

# Confronto struttura (heading, section, label, button)
node bashscripts/design-comuni/verify-parity.mjs
node bashscripts/design-comuni/audit-shell.mjs
php artisan view:clear
php artisan view:cache
git diff --check
```

La verifica deve registrare HTTP status, HTML/DOM, pixel similarity, screenshot, overflow, immagini mancanti, errori console, heading count, focus e contrasto. Target minimo: HTML ≥90%, visual parity ≥98% (o il target esplicito della story), zero console error, zero immagini mancanti e zero overflow. Un risultato sotto soglia è un lavoro aperto, non un pass.

Non usare un confronto artificiale che escluda header/footer, nasconda errori o confronti solo il viewport più favorevole. Se la reference contiene asset esterni non disponibili (es. `picsum.photos`), documentare l'asset e usare un fallback semanticamente equivalente, mantenendo il gap esplicito.

## 9. Loop di implementazione

Per ogni story:

1. acquisisci baseline e screenshot reference;
2. correggi prima dati, routing e composizione dei blocchi (slug JSON → pageSlug);
3. correggi poi geometria condivisa, token, typography, colori e stati interattivi;
4. verifica desktop e mobile;
5. esegui audit WCAG e console;
6. aggiorna story, report parity e documentazione del blocco;
7. salva nel second brain le decisioni durevoli e le correzioni di memoria;
8. passa alla story successiva solo quando la soglia è misurata o il blocker è riproducibile e assegnato.

La priorità è: errori runtime e route, shell condivisa, pagine con similarity più bassa, quindi rifiniture locali. Non aumentare la complessità introducendo configurazioni o componenti non richiesti.
