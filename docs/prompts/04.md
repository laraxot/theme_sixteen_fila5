# Prompt 04 — Evoluzione front-office Sixteen

> Questo documento è un runbook operativo, non una richiesta di riscrittura
> generica del tema: ogni intervento parte da una prova osservabile, corregge
> la causa nel livello proprietario e termina con una prova ripetibile. Se una
> prova non è eseguibile nell'ambiente corrente, va marcata `UNVERIFIED` con il
> primo errore deterministico; non va sostituita con un'ipotesi.

## Filosofia (leggi prima di toccare codice)

FixCity è un servizio pubblico di **segnalazione civica**: il cittadino apre una
segnalazione (foto, luogo, testo); finché è in attesa la vede solo lui; un
moderatore la approva o la scarta (niente piedi, niente bestemmie); poi si
individua il destinatario (ULSS, comune, vigili…), si manda una mail e si
traccia ogni passaggio. Blog ed eventi non sono ornamentali: sono **inbound
marketing istituzionale** (fiducia, trasparenza, partecipazione).

Tre leggi del tema:

1. **JSON = contenuto, Blade = vestito.** Slogan, link, etichette e URL vivono
   nei JSON CMS (`sections/*.json`, `pages/*.json`). La Blade non inventa copy.
2. **Sixteen = Design Comuni.** Stack Tailwind + Alpine + Lit + DaisyUI +
   Flowbite. Bootstrap Italia è solo riferimento tipografico/visuale, mai
   runtime CSS/JS. Il chrome header canonico è
   `resources/views/components/sections/header/v1.blade.php` → `tailwind.blade.php`;
   non creare una seconda implementazione chiamata `design-comuni.blade.php`.
   Eventuali `tpl="design-comuni"` storici riguardano i blocchi/sezioni e non
   autorizzano la creazione di un layout parallelo. La shell canonica del front
   office è esclusivamente `components/layouts/app.blade.php`; non creare alias
   `components/layouts/design-comuni.blade.php` e non selezionarlo dalle pagine.
   La stessa regola vale per il footer: usare `sections/footer/v1.blade.php`;
   `footer/design-comuni.blade.php` non è un entrypoint valido.
3. **Modulo possiede il dominio, tema possiede la resa.** Commenti → modulo
   `Comment` (widget Filament). Ticket/timeline → `Fixcity`. Post/eventi FO →
   `Blog\Article` con `content_type=post|event`. Auth FO → Folio + Volt +
   widget Filament, nessuna route in `web.php`/`api.php` e nessun controller.

Se una richiesta contraddice queste leggi, prevalgono le leggi + il decision
log verificato. Procedi senza chiedere conferma per scelte reversibili;
fermati solo su decisioni di prodotto, accessi esterni o azioni distruttive.

### Contratto unico per header e footer

Sixteen è già il tema Design Comuni: `design-comuni` descrive la capability
del tema, non una variante di ciascuna sezione. Gli entrypoint CMS canonici
sono quindi:

```text
Themes/Sixteen/resources/views/components/sections/header/v1.blade.php
Themes/Sixteen/resources/views/components/sections/footer/v1.blade.php
```

Non creare `sections/header/design-comuni.blade.php` o
`sections/footer/design-comuni.blade.php`: i vecchi file sono stati rimossi e
non sono entrypoint runtime. Se un deploy richiede una migrazione da un JSON
storico, si corregge il dato alla fonte e si verifica che nessun alias
temporaneo venga committato. Il CMS deve usare
`pub_theme::components.sections.{header,footer}.v1`.

Il motivo è architetturale: il nome della view è parte del contratto tra JSON
CMS, `Section`, tema e test. Due renderer con nomi che descrivono la stessa
capability divergono facilmente, fanno scegliere il vestito sbagliato e
possono perfino creare ricorsione se gli alias si puntano a vicenda.

Quando trovi un path `design-comuni`:

1. cerca tutti i riferimenti in JSON, Blade, test e documentazione;
2. sposta il contratto runtime su `header/v1` o `footer/v1`;
3. riduci l'eventuale vecchio file a compatibilità, oppure rimuovilo solo se
   nessun dato storico lo carica;
4. aggiorna il test al proprietario `v1`, senza testare dettagli di un alias;
5. verifica JSON, rendering e localizzazione a 375/768/1440 px.

Un cambio di nome non autorizza a cambiare dominio, contenuti o fallback: la
correzione deve essere una modifica di ownership, non un restyle laterale.

### Regola critica per le pagine CMS di primo livello

`/it/domande-frequenti` è già servita da `pages/[container0]/index.blade.php`:
lo shell costruisce `domande-frequenti.index`, il CMS legge il JSON tenant e
il blocco `content-page` (accordion source `faq`) viene renderizzato da Sixteen.
Non creare mai `resources/views/pages/domande-frequenti/index.blade.php` né la
variante flat `pages/domande-frequenti.blade.php`: sono route concorrenti che
possono bypassare contenuto, localizzazione, header/footer e composizione
Filament. Un difetto va corretto al livello owner (Cms / Fixcity / Sixteen),
non aggiungendo una pagina speciale. Contratto:
[faq-route-ownership.md](../bmad/faq-route-ownership.md).

## Errori già pagati

Non sono suggerimenti: sono cause già viste in produzione. Ripeterle costa un 500 o una pagina illeggibile.

1. **Due JSON, uno slug, pagina giù.** `pages/auth/register.json` insieme a `pages/auth/auth.register.json` produce `matched 2 records for slug [auth.register]`. La sorgente è `auth/auth.register.json`. Non rendere permissivo `findUniqueBySlug()`.
2. **`@volt('nome')` è globale.** Il fragment è l'md5 del nome, non del file. Un prototipo che riusa `auth.login` o `auth.register` sostituisce il vestito vero e la Blade più vecchia non viene ricompilata.
3. **Titolo salvato come testo, card vuota.** Se `articles.title` non è JSON di traduzione, Spatie restituisce stringa vuota. Le card usano `Article::getTitle()`, che legge il valore grezzo.
4. **Dentro `data-dc` le utility Tailwind perdono** contro i reset successivi (`ol`, `button`, `overflow`, chevron `::after`). Quello che si vede è una regola `main[data-page=…]` oppure uno `<style>` nel blocco. Una classe nuova non esiste nel CSS servito finché non parte `npm run build` in `Themes/Sixteen`.
5. **Niente sprite Bootstrap Italia** (`<use href="…/sprites.svg">`). Icone in SVG inline.
6. **Il riferimento statico non è il contenuto.** Colosseo, castello normanno e Gipsoteca non vanno sull'indice eventi FixCity. Un pulsante verso `#` non si pubblica.
7. **Host di prova.** Dal browser dell'agente `192.168.1.40:8000` non risponde. La prova pubblica è `https://fixcity.eu`. Locale corretto e dominio vecchio = `BLOCKED_DEPLOYMENT`, non un altro restyle.
8. **Non creare un account e non entrare con credenziali vere.** Si può spuntare il consenso facoltativo. Non si invia il form di registrazione e non si completa un login.
9. **`graphify-out/graph.json` può mancare.** Non bloccare l'audit per questo.

## Scopo

Esegui un **audit dimostrabile**, poi completa solo i gap. Non aggiungere pagine
isolate: mantieni un unico sistema CMS-driven, accessibile e responsive.

Risultato atteso:

- struttura e linguaggio visuale Design Comuni Italia;
- parity HTML ≥ 90% e visual ≥ 95% sulle pagine dichiarate (esclusi header/footer);
- WCAG 2.1 AA verificata a 375 / 768 / 1440 px;
- prova riproducibile per ogni claim, altrimenti stato `UNVERIFIED` / blocker.

### Caso prioritario: `/it/auth/register`

La registrazione è il percorso critico che trasforma un visitatore in cittadino
abilitato a creare e seguire una segnalazione. Prima di modificare il markup,
verifica nell'ordine seguente:

1. Controlla la risposta pubblica e il documento HTML: `200` in it/en/de/es,
   `lang` della locale, un solo `h1`, un solo form `wire:submit="submit"`.
   Il `<form>` della modale di ricerca del sito non è un secondo modulo di
   registrazione. Non inviare il form.
2. Per la route Folio `auth.register` mantieni una sola sorgente CMS canonica:
   `laravel/config/local/fixcity/database/content/pages/auth/auth.register.json`.
   Non creare né mantenere `pages/auth/register.json`: la collisione produce
   `matched 2 records for slug [auth.register]` e rende indisponibile la pagina.
3. Valida il JSON, le localizzazioni `it/en/de/es` e il blocco `auth.register`;
   copy, etichette e URL non devono essere inventati nella Blade.
4. Verifica il flusso completo: shell Folio sottile → blocco CMS →
   `components/pages/auth-register.blade.php` → widget del modulo GDPR/User.
   La logica di validazione, consenso, creazione utente e mail resta nel modulo.
5. Solo dopo la salute runtime valuta UX/a11y: ordine naturale dei campi,
   error summary annunciato, label/hint/error associati, privacy e termini
   obbligatori, marketing opzionale, password comprensibili, link localizzati,
   focus visibile, target minimo 44 px e nessun overflow a 375 px.

Per `register`, `DONE` richiede: `200` pubblico, JSON unico e valido, test
pertinenti, build Sixteen, controllo a 375/768/1440 px e smoke post-deploy. Se
il codice locale è corretto ma il dominio restituisce ancora 500, lo stato è
`BLOCKED_DEPLOYMENT`, non `DONE`: servono rilascio, invalidazione cache/config
appropriata e una nuova verifica.

## Contesto tecnico — vincoli non negoziabili

- App in `laravel/`; tema in `laravel/Themes/Sixteen/`.
- FO: Folio/Volt + blocchi Blade + widget Filament esistenti.
- Header/footer: `<x-section slug="header|footer">` →
  `laravel/config/local/fixcity/database/content/sections/{header,footer}.json`.
  Il resolver `Modules/Cms/View/Components/Section` usa `v1` come default e
  risolve `tpl` in `components.sections.{slug}.{tpl}`; verificare sempre il
  path proprietario prima di creare o rinominare una view.
- Shell Folio sottili già presenti: `[container0]/index.blade.php` e
  `[container0]/[slug0]` con `PageSlugMiddleware` — non duplicarle.
- Commenti: riusa `CommentsWidget`; niente secondo motore Livewire.
- Auth provider: solo `resources/views/pages/auth/[provider]/index.blade.php`
  (vietato `pages/oauth/`). Preferisci `route('oauth.redirect')` se esiste già
  nel contratto applicativo; non inventare nomi di route.
- Vite tema: `@vite([...], 'themes/Sixteen')` — mai entry senza build name.
- Traduzioni: cinque elementi
  `<namespace>::<contesto>.<collezione>.<chiave>.<tipo>`
  (es. `fixcity::auth.login.intro.text`).
- Contratti PHP: preferisci `UserContract` a `instanceof BaseUser`.
- PHPStan: solo `laravel/phpstan.neon` (l’utente lo modifica).
- Script nuovi → `bashscripts/<categoria>/` + docs in `bashscripts/docs/`.
- Docs nuovi → `docs/` del modulo/tema proprietario; `bmad-output/` legacy.
- Docs di ownership: Cms documenta resolver e shell, Fixcity catalogo e
  fallback, Sixteen renderer e asset. Ogni fatto ha una fonte canonica; gli
  altri documenti devono linkarla, non duplicarla.
- Tipografia FO (D18 / DCP-221): l'h1 home è **Lora Regular 400** tramite
  la regola `.fc-home-hero h1` (clamp 2.5–3rem, lh 1.2). Non aggiungere la
  utility `font-serif`: in `resources/css/thematic/tailwind.css` il token
  `--font-serif` è Titillium e la classe può annullare Lora. Titoli sans UI
  = Titillium **≤ 600**. Vietato 750/800/900 su Titillium (fallback Black).
- Trait `TypedHasRecursiveRelationships` già rimosso: usare
  `Staudenmeir\LaravelAdjacencyList\Eloquent\HasRecursiveRelationships` +
  `HasRecursiveRelationshipsContract`.

### Ordine di indagine per ogni pagina

1. Contratto della route/Folio e risposta HTTP reale.
2. Sorgente CMS e collisioni di slug (conteggio esplicito, non solo `git grep`).
3. Shell e componenti riusabili del tema.
4. Widget, azioni e regole del modulo proprietario.
5. Traduzioni e URL localizzati.
6. Test, build, a11y e verifica responsive.

Non correggere una collisione rendendo il resolver permissivo o scegliendo
silenziosamente il primo record: la duplicazione dei dati va eliminata alla
fonte e il rilevatore di collisioni resta una protezione intenzionale.

### Classificazione obbligatoria degli esiti

Ogni errore va assegnato a una sola causa primaria, per evitare fix nel livello
sbagliato:

- `CODE`: il contratto o il rendering locale è errato;
- `CONTENT`: JSON mancante, invalido, non localizzato o duplicato;
- `DEPLOYMENT`: locale corretto, ma artefatti/cache/config sul dominio non
  aggiornati;
- `ENVIRONMENT`: test non avviabile per DB, bootstrap, fixture o servizio
  assente;
- `PRODUCT`: manca una decisione esplicita su copy, flusso o comportamento.

Il report deve contenere URL/path, comando, risposta o primo errore, causa
classificata, file proprietario da correggere e prova di chiusura. Un `200`
pubblico non dimostra da solo la correttezza del flusso: controlla anche
contenuto CMS, interazione, localizzazione e stato degli errori.

### 2. Piano BMAD minimo

Nei `docs/` proprietari: brief, architettura confini, story ordinate, decision
log, report parity/a11y. Ogni story: file, precondizioni, AC, prova, stato.

## Ambiti funzionali

### A. Shell header/footer

- Una sola `<x-section>` header e una footer per layout.
- Per Sixteen l'header applicativo passa da `tpl="v1"`; il tema non deve
  moltiplicare il nome del design nel path del renderer.
- Dati da JSON; logo leggibile su fondo scuro (bianco se serve contrasto).
- Link blog/eventi già in JSON: verifica resa e localizzazione, non seconda fonte.
- Mobile: niente striscia bianca sotto header; skip link; focus; menu tastiera.

### B. Tipografia e a11y (DCP-221)

- Hero «Segnalazioni e servizi per la tua comunità»: **Lora 400**, clamp
  2.5–3rem, lh 1.2, colore bianco su fondo scuro. Il contratto è il selettore
  `.fc-home-hero h1` in `resources/css/app/16-homepage-civic-reframe.css`.
  La prova è il computed style, non una classe sull'elemento.
- Altri titoli home: Titillium 600.
- Font via Vite (`laravel-vite-plugin/fonts` + `fonts.css` locali).
- Contrasto 4.5:1 / 3:1, focus, zoom, `prefers-reduced-motion`, no overflow.

### D. Commenti e dettaglio segnalazione

- Widget Comment su blog, eventi, ticket (guest = read-only).
- Timeline ticket null-safe: segnalato → approvato/scartato → mail inviata → risposta.
- Reference composizione: schede Design Comuni graduatoria/permessi/vantaggi
  (tempi, prossimi passi) — logica dominio resta in Fixcity.

### E. Autenticazione

- Login: credenziali + Google + link register + password reset.
- Folio auth; JSON CMS `auth.login`; stessa filosofia di `pages/index.blade.php`.
- Spinner/progress accessibile al submit (Alpine; pattern ispirato a BI Progress,
  implementato nello stack del tema).
- Register e FAQ allineati a Design Comuni.

#### Acceptance criteria register

- `GET /{locale}/auth/register` restituisce `200` per ogni locale supportato;
- esiste un solo documento CMS per il conteggio semantico `auth.register`;
- heading/intro arrivano dal blocco CMS, con fallback sicuro documentato;
- il form conserva nome, cognome, email, password, conferma password, privacy,
  termini e marketing opzionale;
- gli errori sono percepibili senza affidarsi al solo colore e non cancellano
  i valori non sensibili;
- il submit non duplica richieste durante il loading e resta usabile da tastiera;
- privacy/termini puntano alle pagine localizzate e il login è localizzato;
- non vengono introdotti controller, route o componenti di registrazione paralleli;
- ogni prova registra comando, esito (`PASS`/`FAIL`/`UNVERIFIED`), ambiente e data.

### F. Qualità strutturale

- Migrazioni Fixcity: ownership reale, non «N modelli = N migrazioni» cieco.
- Package Sixteen: dipendenze aggiornate solo con story + verifica build.
- Boy scout: correggi ciò che trovi; alza qualità; PHPStan a zero sul codice toccato.

# Prompt 04 — Evoluzione front-office Sixteen

> Questo documento è un runbook operativo, non una richiesta di riscrittura
> generica del tema: ogni intervento parte da una prova osservabile, corregge
> la causa nel livello proprietario e termina con una prova ripetibile. Se una
> prova non è eseguibile nell'ambiente corrente, va marcata `UNVERIFIED` con il
> primo errore deterministico; non va sostituita con un'ipotesi.

## Filosofia (leggi prima di toccare codice)

FixCity è un servizio pubblico di **segnalazione civica**: il cittadino apre una
segnalazione (foto, luogo, testo); finché è in attesa la vede solo lui; un
moderatore la approva o la scarta (niente piedi, niente bestemmie); poi si
individua il destinatario (ULSS, comune, vigili…), si manda una mail e si
traccia ogni passaggio. Blog ed eventi non sono ornamentali: sono **inbound
marketing istituzionale** (fiducia, trasparenza, partecipazione).

Tre leggi del tema:

1. **JSON = contenuto, Blade = vestito.** Slogan, link, etichette e URL vivono
   nei JSON CMS (`sections/*.json`, `pages/*.json`). La Blade non inventa copy.
2. **Sixteen = Design Comuni.** Stack Tailwind + Alpine + Lit + DaisyUI +
   Flowbite. Bootstrap Italia è solo riferimento tipografico/visuale, mai
   runtime CSS/JS. Il chrome header canonico è
   `resources/views/components/sections/header/v1.blade.php` → `tailwind.blade.php`;
   non creare una seconda implementazione chiamata `design-comuni.blade.php`.
   Eventuali `tpl="design-comuni"` storici riguardano i blocchi/sezioni e non
   autorizzano la creazione di un layout parallelo. La shell canonica del front
   office è esclusivamente `components/layouts/app.blade.php`; non creare alias
   `components/layouts/design-comuni.blade.php` e non selezionarlo dalle pagine.
   La stessa regola vale per il footer: usare `sections/footer/v1.blade.php`;
   `footer/design-comuni.blade.php` non è un entrypoint valido.
3. **Modulo possiede il dominio, tema possiede la resa.** Commenti → modulo
   `Comment` (widget Filament). Ticket/timeline → `Fixcity`. Post/eventi FO →
   `Blog\Article` con `content_type=post|event`. Auth FO → Folio + Volt +
   widget Filament, nessuna route in `web.php`/`api.php` e nessun controller.

Se una richiesta contraddice queste leggi, prevalgono le leggi + il decision
log verificato. Procedi senza chiedere conferma per scelte reversibili;
fermati solo su decisioni di prodotto, accessi esterni o azioni distruttive.

### Contratto unico per header e footer

Sixteen è già il tema Design Comuni: `design-comuni` descrive la capability
del tema, non una variante di ciascuna sezione. Gli entrypoint CMS canonici
sono quindi:

```text
Themes/Sixteen/resources/views/components/sections/header/v1.blade.php
Themes/Sixteen/resources/views/components/sections/footer/v1.blade.php
```

Non creare `sections/header/design-comuni.blade.php` o
`sections/footer/design-comuni.blade.php`: i vecchi file sono stati rimossi e
non sono entrypoint runtime. Se un deploy richiede una migrazione da un JSON
storico, si corregge il dato alla fonte e si verifica che nessun alias
temporaneo venga committato. Il CMS deve usare
`pub_theme::components.sections.{header,footer}.v1`.

Il motivo è architetturale: il nome della view è parte del contratto tra JSON
CMS, `Section`, tema e test. Due renderer con nomi che descrivono la stessa
capability divergono facilmente, fanno scegliere il vestito sbagliato e
possono perfino creare ricorsione se gli alias si puntano a vicenda.

Quando trovi un path `design-comuni`:

1. cerca tutti i riferimenti in JSON, Blade, test e documentazione;
2. sposta il contratto runtime su `header/v1` o `footer/v1`;
3. riduci l'eventuale vecchio file a compatibilità, oppure rimuovilo solo se
   nessun dato storico lo carica;
4. aggiorna il test al proprietario `v1`, senza testare dettagli di un alias;
5. verifica JSON, rendering e localizzazione a 375/768/1440 px.

Un cambio di nome non autorizza a cambiare dominio, contenuti o fallback: la
correzione deve essere una modifica di ownership, non un restyle laterale.

### Regola critica per le pagine CMS di primo livello

`/it/domande-frequenti` è già servita da `pages/[container0]/index.blade.php`:
lo shell costruisce `domande-frequenti.index`, il CMS legge il JSON tenant e
il blocco `content-page` (accordion source `faq`) viene renderizzato da Sixteen.
Non creare mai `resources/views/pages/domande-frequenti/index.blade.php` né la
variante flat `pages/domande-frequenti.blade.php`: sono route concorrenti che
possono bypassare contenuto, localizzazione, header/footer e composizione
Filament. Un difetto va corretto al livello owner (Cms / Fixcity / Sixteen),
non aggiungendo una pagina speciale. Contratto:
[faq-route-ownership.md](../bmad/faq-route-ownership.md).

## Errori già pagati

Non sono suggerimenti: sono cause già viste in produzione. Ripeterle costa un 500 o una pagina illeggibile.

1. **Due JSON, uno slug, pagina giù.** `pages/auth/register.json` insieme a `pages/auth/auth.register.json` produce `matched 2 records for slug [auth.register]`. La sorgente è `auth/auth.register.json`. Non rendere permissivo `findUniqueBySlug()`.
2. **`@volt('nome')` è globale.** Il fragment è l'md5 del nome, non del file. Un prototipo che riusa `auth.login` o `auth.register` sostituisce il vestito vero e la Blade più vecchia non viene ricompilata.
3. **Titolo salvato come testo, card vuota.** Se `articles.title` non è JSON di traduzione, Spatie restituisce stringa vuota. Le card usano `Article::getTitle()`, che legge il valore grezzo.
4. **Dentro `data-dc` le utility Tailwind perdono** contro i reset successivi (`ol`, `button`, `overflow`, chevron `::after`). Quello che si vede è una regola `main[data-page=…]` oppure uno `<style>` nel blocco. Una classe nuova non esiste nel CSS servito finché non parte `npm run build` in `Themes/Sixteen`.
5. **Niente sprite Bootstrap Italia** (`<use href="…/sprites.svg">`). Icone in SVG inline.
6. **Il riferimento statico non è il contenuto.** Colosseo, castello normanno e Gipsoteca non vanno sull'indice eventi FixCity. Un pulsante verso `#` non si pubblica.
7. **Host di prova.** Dal browser dell'agente `192.168.1.40:8000` non risponde. La prova pubblica è `https://fixcity.eu`. Locale corretto e dominio vecchio = `BLOCKED_DEPLOYMENT`, non un altro restyle.
8. **Non creare un account e non entrare con credenziali vere.** Si può spuntare il consenso facoltativo. Non si invia il form di registrazione e non si completa un login.
9. **`graphify-out/graph.json` può mancare.** Non bloccare l'audit per questo.

## Scopo

Esegui un **audit dimostrabile**, poi completa solo i gap. Non aggiungere pagine
isolate: mantieni un unico sistema CMS-driven, accessibile e responsive.

Risultato atteso:

- struttura e linguaggio visuale Design Comuni Italia;
- parity HTML ≥ 90% e visual ≥ 95% sulle pagine dichiarate (esclusi header/footer);
- WCAG 2.1 AA verificata a 375 / 768 / 1440 px;
- prova riproducibile per ogni claim, altrimenti stato `UNVERIFIED` / blocker.

### Caso prioritario: `/it/auth/register`

La registrazione è il percorso critico che trasforma un visitatore in cittadino
abilitato a creare e seguire una segnalazione. Prima di modificare il markup,
verifica nell'ordine seguente:

1. Controlla la risposta pubblica e il documento HTML: `200` in it/en/de/es,
   `lang` della locale, un solo `h1`, un solo form `wire:submit="submit"`.
   Il `<form>` della modale di ricerca del sito non è un secondo modulo di
   registrazione. Non inviare il form.
2. Per la route Folio `auth.register` mantieni una sola sorgente CMS canonica:
   `laravel/config/local/fixcity/database/content/pages/auth/auth.register.json`.
   Non creare né mantenere `pages/auth/register.json`: la collisione produce
   `matched 2 records for slug [auth.register]` e rende indisponibile la pagina.
3. Valida il JSON, le localizzazioni `it/en/de/es` e il blocco `auth.register`;
   copy, etichette e URL non devono essere inventati nella Blade.
4. Verifica il flusso completo: shell Folio sottile → blocco CMS →
   `components/pages/auth-register.blade.php` → widget del modulo GDPR/User.
   La logica di validazione, consenso, creazione utente e mail resta nel modulo.
5. Solo dopo la salute runtime valuta UX/a11y: ordine naturale dei campi,
   error summary annunciato, label/hint/error associati, privacy e termini
   obbligatori, marketing opzionale, password comprensibili, link localizzati,
   focus visibile, target minimo 44 px e nessun overflow a 375 px.

Per `register`, `DONE` richiede: `200` pubblico, JSON unico e valido, test
pertinenti, build Sixteen, controllo a 375/768/1440 px e smoke post-deploy. Se
il codice locale è corretto ma il dominio restituisce ancora 500, lo stato è
`BLOCKED_DEPLOYMENT`, non `DONE`: servono rilascio, invalidazione cache/config
appropriata e una nuova verifica.

### Classificazione obbligatoria degli esiti

Ogni errore va assegnato a una sola causa primaria, per evitare fix nel livello
sbagliato:

- `CODE`: il contratto o il rendering locale è errato;
- `CONTENT`: JSON mancante, invalido, non localizzato o duplicato;
- `DEPLOYMENT`: locale corretto, ma artefatti/cache/config sul dominio non
  aggiornati;
- `ENVIRONMENT`: test non avviabile per DB, bootstrap, fixture o servizio
  assente;
- `PRODUCT`: manca una decisione esplicita su copy, flusso o comportamento.

Il report deve contenere URL/path, comando, risposta o primo errore, causa
classificata, file proprietario da correggere e prova di chiusura. Un `200`
