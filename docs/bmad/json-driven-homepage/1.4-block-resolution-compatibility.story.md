# Story

Come manutentore, voglio che il resolver CMS trovi ogni block view e propaghi i
dati corretti, così che il passaggio a JSON non introduca fallback silenziosi.

## Acceptance criteria

- [ ] `BlockData` risolve view Sixteen esistenti e conserva `active`.
- [ ] Le query dichiarate nel blocco sono risolte dal resolver previsto.
- [ ] I dati contestuali non sovrascrivono chiavi del blocco senza contratto.
- [ ] Ogni view mancante fallisce con diagnostica utile o viene classificata.
- [ ] Nessun cambiamento a `phpstan.neon` o introduzione di ignore.

## Tasks

- [ ] Verificare `BlockData`, `Page` e `cms::components.page`.
- [ ] Testare alias/namespace `pub_theme::components.blocks`.
- [ ] Documentare incompatibilità residue e piano di compatibilità.

## Dev notes (locked)

Il renderer usa `@include($block->view, array_merge(...))`; il tema non deve
replicare questa logica. [Source: architecture.md#componenti-e-responsabilità]

## Testing plan (locked)

Unit test `BlockData` e page component con view valida, view mancante, blocco
inattivo e query dinamica.

## Owned file/module scope

- `laravel/Modules/Cms/app/Datas/BlockData.php` (solo se necessario)
- `laravel/Modules/Cms/resources/views/components/page.blade.php`
- `laravel/Themes/Sixteen/resources/views/components/blocks/`
